What the browser derives (never sent or stored as-is)

From the password:

ncryptsec_password = NIP-49 encryption of the key (scrypt, random salt inside)
auth_password = PBKDF2(password, salt "yourapp-auth:" + username)

From the recovery code (random, generated by the app):

ncryptsec_recovery = NIP-49 encryption of the same key
auth_recovery = PBKDF2(code, salt "yourapp-recovery:" + username)

The different prefixes keep the two authentication values independent.

What the server stores per user
Field	Content
username	Unique, normalized (trimmed, lowercase, NFKC)
pubkey	The user's public key (hex)
ncryptsec_password	Key encrypted with the password
ncryptsec_recovery	Key encrypted with the recovery code
auth_hash_password	argon2 hash of auth_password
auth_hash_recovery	argon2 hash of auth_recovery
kdf_version	Parameter version, for future migrations
failed_attempts, locked_until	Rate limiting
created_at, updated_at	Timestamps

Never stored, and never sent: the password, the recovery code, the raw private key.
Sent at login but never stored: the authentication values.

Server endpoints

POST /signup: receives username, pubkey, both ncryptsec values, and both authentication values. The request includes a NIP-98 signature, proving the user holds the private key for pubkey, which stops anyone registering someone else's public key. The server hashes both authentication values with argon2 and stores everything.

POST /login: receives username + auth_password. If the argon2 check passes, it returns ncryptsec_password. Otherwise it returns a generic error and counts the attempt.

POST /recover: receives username + auth_recovery. If it passes, it returns ncryptsec_recovery.

PUT /credentials: authenticated with NIP-98. Replaces the ncryptsec values and authentication hashes, used after a password change or recovery.

GET /.well-known/nostr.json: optional NIP-05 file, built from the usernames and public keys.

The flows

New user: the browser generates a key and a recovery code, derives everything, shows the recovery kit, then calls /signup.

Existing user with their own key: the same as a new user, except they paste their key instead of generating one.

Login: the browser computes auth_password and calls /login, then decrypts the returned ncryptsec locally. The key stays in memory for the session.

Forgotten password: the browser computes auth_recovery and calls /recover, then decrypts the returned ncryptsec. The user chooses a new password, and the app generates a new recovery code and shows the new kit. The browser derives everything again and calls /credentials.

Signer users (NIP-07 or NIP-46): no server record is needed, since their key never touches your app. If you offer NIP-05 names, a username-to-pubkey row is enough.

What protects what
A stranger with a username gets nothing without passing the server's check, and the check is rate-limited.
A stolen database contains only argon2 hashes, which can't be replayed, and ncryptsec values, which are slow to attack.
Your server never sees anything that decrypts a key, so the design stays non-custodial.
